## Публичный чат

Frontend отправляет `POST /api/chat` в Go с `X-Request-ID` длиной 8–128
символов. При повторе запроса ключ и тело должны остаться прежними. Go выдаёт
HttpOnly-cookie `demo_chat`; она идентифицирует только демонстрационную сессию,
не пользователя Авито.

Если `AI_INTERNAL_TOKEN` пуст, Backend сохраняет прежний путь: распознаёт
ограниченные демо-команды сам, а прочие вопросы проксирует в Python `POST /chat`.
Python возвращает `{reply, sources:[{title,url}]}`.

Если `AI_INTERNAL_TOKEN` содержит не менее 32 символов, Backend направляет все
сообщения в `POST /agent/step` и передаёт credential только в
`X-AI-Internal-Token`. Один и тот же токен нужно задать Backend и AI через
локальный `.env`; его нельзя передавать браузеру или коммитить.

## Demo-agent flow

Go сам формирует и ограничивает доверенный для этого demo контекст:

- пользователь `demo-intern-001`, роль `Intern`, команда `demo-team`, неделя 1;
- каталог сервисов для заявок: Jira и Confluence;
- синтетические сервисы и владельцы для сценария поиска: billing/search и
  `demo-owner-billing`/`demo-owner-search`;
- имя получателя и текст сообщения берутся из сохранённого сервером черновика,
  а не из пользовательского подтверждения.

Python может вернуть только `answer` или одно типизированное предложение
`tool_call`. Go повторно проверяет имя и аргументы: заявка создаётся только при
явном запросе и для Jira/Confluence; поиск владельца ограничен синтетическим
каталогом; `send_message` допустим только после подтверждения неизменённого
черновика. Реальная Jira, IAM и доставка сообщений сотрудникам не вызываются.

Заявка/сообщение и ответ на тот же `X-Request-ID` сохраняются транзакционно в
Postgres. Повтор того же ключа с тем же текстом возвращает сохранённый ответ;
тот же ключ с другим текстом даёт 409. Успех пользователю сообщает Go по
сохранённому ID/status, а не только по тексту модели. Результат tool передаётся
в Python как `tool_result` для продолжения. Контекст сессии ограничен cookie,
имеет TTL и не является авторизацией.

## Локальная настройка и проверка

1. В `.env` задайте `AI_INTERNAL_TOKEN` результатом `openssl rand -hex 32`.
   Не перезаписывайте существующие переменные и не коммитьте `.env`.
2. Убедитесь, что одинаковый token настроен для Backend и AI в Compose:

   ```bash
   docker compose config -q
   docker compose up -d --build
   docker compose ps
   ```

3. Пройдите в браузере три сценария:
   - SPT: ответ содержит разрешённую ссылку-источник;
   - неизвестный термин: честный ответ без источников;
   - заявка: один сохранённый ID и статус; поиск владельца: проверить черновик,
     затем подтвердить или отменить и проверить запись в mock-таблице.
4. Для повторной отправки используйте тот же request key; не создавайте новый
   ключ, если исход исходного сетевого запроса неизвестен.

Backend: `TEST_DATABASE_URL=... go test ./...`; AI:
`docker compose exec -T ai-service pytest -q`; Frontend:
`cd frontend && npm run test:coverage`.

## Проверенное и оставшееся

- Go ↔ Python RAG smoke-тест возвращал HTTP 200 по SPT с pinned Playbook source;
  неизвестный термин — честный отказ.
- Backend unit/integration tests проходят на изолированной `aibuddy_test`,
  включая создание заявки, идемпотентный повтор, поиск синтетического owner,
  подтверждение сообщения и защиту от лишних tool-аргументов.
- AI pytest: 87 passed, 5 skipped; Frontend tests: 22 passed.
- Реальный Qwen flow проверен через браузер: создана `DEMO-ACCESS-3`, найден
  синтетический владелец billing, после явного подтверждения сохранено
  `DEMO-MSG-3`. Никакие реальные системы/пользователи не затронуты.
- После пересоздания Backend старый Nginx upstream давал 502 из-за сохранённого
  IP контейнера. В `frontend/nginx.conf` включено повторное разрешение Compose
  DNS; proxy после пересоздания контейнеров проверен повторно.

Ограничения до production-like решения: нет IAM и подтверждённой личности
пользователя; synthetic user/context и owner directory — только фикстуры; нет
SSE и реальных Jira/Mattermost adapters. Этот demo-контур нельзя считать
корпоративной авторизацией или подключать к реальным write-интеграциям.
