Локальная embeddinggemma, 768 измерений, cosine distance ≤0,35, top_k=3.
Для каждого вопроса применялись действующие definition_query и expand_query,
затем embedding, Repository.search и term_matches из RAG. Для положительных
вопросов успех означает присутствие ожидаемой пары document_id/section в
итоговой выдаче. Это точечная оценка разделов, не процент правильных ответов LLM.

Положительные вопросы проверены одними и теми же векторами на индексе до
переиндексации (16 чанков) и после (27 чанков). Модели и пороги не менялись.

## Повторение проверки

1. Проверить модели и настройки по ../DEPLOYMENT.md.
2. Выполнить `docker compose exec ai-service python -m ingest`.
3. Для каждого question из knowledge.json вычислить
   `Provider.embed([expand_query(definition_query(question) or question)])[0]`.
4. Получить `Repository.search(vector)`, затем оставить только чанки, в которых
   каждый латинский термин вопроса проходит `term_matches(term, chunk.text)`.
5. Сравнить document_id/section с ожидаемыми; для no_context проверить пустоту.
6. Отдельно отправить вопросы через /api/chat и проверить содержание, источник,
   отсутствие выдуманных деталей. needs_team_context нельзя оценить одним
   фактом наличия retrieved chunks.

Старый индекс не восстанавливать поверх пользовательской БД ради сравнения.
Для повторения before-среза нужна изолированная тестовая БД с прошлым корпусом.
Сам файл с вопросами никогда не передавать в ingest как источник знаний.
