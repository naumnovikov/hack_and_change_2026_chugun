Для каждого вопроса применялись действующие definition_query и expand_query,
затем embedding, Repository.search и term_matches из RAG. Для положительных
вопросов успех означает присутствие ожидаемой пары document_id/section в
итоговой выдаче. Это точечная оценка разделов, не процент правильных ответов LLM.

Положительные вопросы проверены одними и теми же векторами на индексе до
переиндексации (16 чанков) и после (27 чанков). Модели и пороги не менялись.

## Повторение проверки

### Итог с гибридным поиском

Для корпуса из 27 чанков поиск дополнен лексическим каналом PostgreSQL
с русской морфологией. Векторные кандидаты с прежним порогом 0,35 имеют
приоритет; лексические дополняют выдачу до прежнего top_k=3. Лексическому
совпадению нужны слово в заголовке документа/раздела, минимум два совпавших
лексемных термина и покрытие не менее половины лексем вопроса. Исключение —
точное определение латинской аббревиатуры, присутствующей в заголовке.
Все латинские термины всё равно должны подтверждаться текстом/алиасами.
При пустой выдаче расширенного запроса повторяется исходный запрос.

Оба канала ограничены текущей коллекцией и `source_type=public`. Проверка
цитат не менялась. Порог cosine не увеличивался; дополнение по лексемам —
самостоятельный путь поиска с отдельными условиями, а не прохождение
лексических кандидатов через векторный порог.

| Выборка | Результат |
|---|---|
| Основная: ожидаемый раздел | 17/17 (ранее 9/17 после расширения корпуса) |
| Дополнительные перефразировки heldout.json | 5/6 |
| Отрицательные примеры обеих выборок | пустая выдача |

В дополнительной выборке не найден короткий вопрос «Зачем нужны дашборды
и алерты?». Более полный вопрос с указанием сервиса из основной выборки
находит материал. Не скрываем ограничение и не считаем эти небольшие выборки
доказательством универсальной точности. Основная выборка использовалась при
разработке; дополнительные перефразировки проверены после выбора правил.

Повторить текущую версию (вызывается настроенный embedding API, возможна
тарификация при внешнем провайдере; генерация ответа LLM не запускается):

```powershell
docker compose exec -T ai-service python evaluations/evaluate.py
docker compose exec -T ai-service python evaluations/evaluate.py evaluations/heldout.json
```

Скрипт выводит только вопросы, ссылки на ожидаемые разделы и результаты,
без ключей или DSN. Прежняя методика ниже описывает исторический векторный
baseline; для итогового гибридного результата используйте скрипт выше.

1. Проверить модели и настройки по ../DEPLOYMENT.md.
2. Выполнить `docker compose exec ai-service python -m ingest`.
3. Для каждого question из knowledge.json вычислить
   `Provider.embed([expand_query(definition_query(question) or question)])[0]`.
4. Получить `Repository.search(vector)`, затем оставить только чанки, в которых
   каждый латинский термин вопроса проходит `term_matches(term, chunk.text)`.
5. Сравнить document_id/section с ожидаемыми; для no_context проверить пустоту.
6. Отдельно отправить вопросы через /api/chat и проверить содержание, источник,
   отсутствие выдуманных деталей. needs_team_context нельзя оценить одним
   фактом наличия retrieved chunks.

Старый индекс не восстанавливать поверх пользовательской БД ради сравнения.
Для повторения before-среза нужна изолированная тестовая БД с прошлым корпусом.
Сам файл с вопросами никогда не передавать в ingest как источник знаний.
