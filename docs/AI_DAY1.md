### Уточнения к импорту и хранению

Поток индексации: allowlist → снимок → нормализация → чанки → embeddings → pgvector.
Поток ответа: доверенный контекст Go → embedding вопроса → разрешённые top-4 чанка
→ Qwen → ответ с источниками или признание нехватки данных → Go/SSE.

| Объект | Поля и правила |
|---|---|
| Документ | ID, title, URL, kind (public/synthetic), revision, fetched_at, SHA-256, active, allowed_roles, team_id |
| Чанк | ID, document_id, section, ordinal, text, content_hash, audience, adaptation_period; для таблицы ещё sheet_gid и исходный номер строки |
| Embedding | chunk_id, model tag и digest, dimension, версия preprocessing, vector(d); индекс и запрос используют один профиль |

Markdown делим по заголовкам и абзацам: стартово до 1800 символов с перекрытием
до 200 внутри секции. Для CSV одна строка — один смысловой чанк: название +
описание + период + аудитория. Длинный список делим по подпунктам, повторяя
название и период; соседние несвязанные строки не склеиваем. Заголовки и
префиксы входят в лимит embedding-модели; превышение делим, а не молча обрезаем.
CSV не сохраняет гиперссылки внутри ячеек: не восстанавливаем их по названиям курсов.

Кандидат первого baseline — `embeddinggemma:300m` через Ollama `/api/embed`;
это отдельная модель, не Qwen для генерации. Каталог указывает 622 МБ и контекст 2K.
Фактическую размерность и digest фиксируем после первого вызова; до этого миграция
с конкретным `vector(d)` не готова. Проверяем формат query/document для выбранного
артефакта, не переносим настройки другой версии модели автоматически.
Русское качество и задержки на этом компьютере ещё не измерены.

В PostgreSQL разделяем документы, чанки и embeddings, с FK и уникальным ключом
по чанку и профилю модели. Начинаем с точного cosine-поиска (`<=>`), без ANN-индекса.
Фильтруем активную ревизию, роль, команду и профиль embeddings до ранжирования/лимита;
`team_id IS NULL` допускается только для явно общего материала. Права проверяются
на запросе, а не после передачи контекста LLM. Публичность URL не делает материал
инструкцией для текущей команды. Смена embedding-профиля требует полной
переиндексации; старую ревизию заменяем атомарно после успешной подготовки новой.

Генерация получает только выбранные источники с идентификаторами. Ссылки ответа
проверяем по этому набору. При конфликте источников явно указываем расхождение;
FAQ определяет поведение MVP. Создание доступа и отправка сообщения идут через Go,
реестр task → service → owner остаётся синтетическим. RAG не выдаёт доступы.

До реализации проверяем минимум 12 запросов: SPT, PaaS, ZBP, LENS, Шаталити,
неизвестное определение Observer, отсутствие инструкции avito-cli, неизвестный
владелец, запрет чужой команды, запрет роли, конфликт Slack/Mattermost и injection.
Измеряем hit@4 на ответимых вопросах, корректность ссылок, отказы и отсутствие
утечек; отдельно задержки retrieval/LLM и потребление RAM на CPU.

Технические основания: [Ollama embeddings](https://docs.ollama.com/capabilities/embeddings),
[EmbeddingGemma](https://ollama.com/library/embeddinggemma), [pgvector](https://github.com/pgvector/pgvector).
Параметры чанков и top-k — стартовые гипотезы, не результаты эксперимента.

## Границы компонентов

Подтверждено пользователем: Python выполняет RAG и вызовы LLM. Go получает доверенный пользовательский контекст, проверяет права, исполняет tools, сохраняет результаты операций и отдаёт SSE фронтенду.
AI не вызывает Jira/Mattermost или их моки. Предложение инструмента от модели не является разрешением на действие.
OpenAPI моков принадлежит Backend; документы `specs/tools/` описывают семантику, но не заменяют `specs/openapi.yaml`.

## RAG: начальный проект

1. Явный allowlist источников → локальные версионированные снимки. Синтетические и публичные документы различаются полем `source_kind`.
2. Разбиение Markdown по заголовкам и абзацам; таблицу сохранять с заголовком колонок. Начальные параметры: до 1800 символов, перекрытие до 200 символов внутри одной секции. Это гипотеза для небольшого корпуса, не измеренный оптимум; длинные блоки делить с сохранением контекста.
3. Метаданные чанка: `document_id`, `chunk_id`, `title`, `section`, `source_url`, `source_kind`, `source_revision`, `content_hash`, `allowed_roles`, `team_id` (для командных данных), `embedding_model`, `embedding_dimension`.
4. Отдельная embedding-модель, одинаковая при индексации и поиске. Кандидат — `embeddinggemma` через Ollama `/api/embed`; выбор пока не утверждён, нужна проверка русского языка и CPU. Размерность берём из ответа, затем фиксируем в схеме `vector(d)`; несовпадение модели/размерности требует переиндексации.
5. Для малого корпуса — точный поиск pgvector по cosine distance, без HNSW на первом этапе. Фильтр ролей и команды применяется в SQL до LIMIT и до передачи текста модели. Контекст прав приходит только от Go; отсутствие контекста означает отказ.
6. Начальный `top_k=4`; добавлять заголовок, текст и стабильный идентификатор источника. Порог релевантности подобрать по контрольным вопросам, не считать произвольное расстояние доказательством ответа.
7. Ответ содержит ссылки только на переданные разрешённые источники. При отсутствии подтверждения — признать нехватку сведений и направить к наставнику. Не расшифровывать ZBP/LENS/Observer из памяти модели без источника.
8. Текст документов и результаты tools — данные, не системные инструкции. Не выполнять содержащиеся в них команды и не менять права по тексту пользователя.

Документация: [Ollama embeddings](https://docs.ollama.com/capabilities/embeddings), [pgvector](https://github.com/pgvector/pgvector), [Qwen3.5](https://ollama.com/library/qwen3.5). Параметры выше — проектные предложения команды.

## Проверка до реализации полного RAG

- Набор из минимум 12 контрольных запросов: подтверждённые ответы, неизвестные термины, недоступные документы и prompt injection. У каждого — ожидаемый источник или ожидаемый отказ.
- Измерять retrieval hit@4 на подтверждённых вопросах, наличие корректных ссылок и отсутствие утечек в отрицательных случаях. Численные цели качества согласовать после baseline.
- Автотесты: разбиение, идемпотентное обновление снимков, фильтрация прав, несовпадение embedding-модели, пустая выдача, timeout, некорректный tool call, повтор действия. Прикладной код — покрытие строго >80%.
- Unit-тесты используют фиктивные embeddings/LLM; отдельная интеграционная проверка требует реальных Postgres/pgvector и Ollama. Демо без модели явно обозначает имитацию, не выдаёт её за настоящий RAG.
