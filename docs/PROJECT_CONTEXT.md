## Что мы строим

AI-buddy — веб-чат для адаптации стажёров Авито. Помощник объясняет внутренние инструменты по разрешённым материалам, помогает оформить доступ через mock API и найти владельца микросервиса для запроса на ревью. Он сокращает рутинные обращения к наставнику и помогает стажёру перейти к самостоятельным задачам.

Наш MVP включает ровно три сценария из `docs/CJM.md`:

1. **«Быстрый старт»** — создание mock-заявки на доступ, показ и сохранение её номера и статуса.
2. **«Переводчик с Авито»** — RAG-ответ на вопрос о внутреннем термине с проверяемым разрешённым источником либо честное сообщение о нехватке данных.
3. **«Кто на кнопке?»** — поиск владельца сервиса и отправка запроса на ревью через mock API после подтверждения сообщения.

**«Проактивный Штурман»** — только roadmap. Реализация возможна после готовности трёх базовых сценариев, тестов и Docker-запуска, по отдельному решению команды.

## Стек и архитектура

- **Backend:** Go 1.22, HTTP API, mock-интеграции, работа с Postgres и контроль корпоративных действий.
- **Frontend:** React + TypeScript + Vite + Zustand + Zod; Vitest и React Testing Library.
- **AI:** Python + FastAPI, Ollama; модель по `.env.example`, Compose и беклогу — `qwen3.5:4b`.
- **БД:** PostgreSQL 16 + pgvector.
- **Инфраструктура:** Docker Compose и GitHub Actions.
- **SDD:** спецификации в `specs/`, подход на базе spec-kit. Наличие документа не означает готовность реализации.

Разделение Go/Python зафиксировано в `specs/agent.spec.md`: **Python ищет RAG-контекст и вызывает LLM; Go проверяет права, валидирует и выполняет tools, сохраняет результаты.** Старое описание RAG и генерации внутри Go не следует использовать как актуальную архитектуру.

Целевой поток Дня 2:

1. Браузер отправляет сообщение в согласованный Go endpoint, а не напрямую в AI.
2. Go валидирует запрос и вызывает AI по `AI_SERVICE_URL` с таймаутом.
3. AI ищет релевантные разрешённые чанки в pgvector и обращается к Ollama с найденным контекстом.
4. Если подтверждённого контекста нет, AI сообщает об этом, не выдумывая ответ. Сбои Ollama и Postgres возвращаются как согласованные ошибки.
5. AI возвращает ответ и источник по контракту; Go передаёт результат Frontend.
6. Frontend показывает ответ, источник, ожидание или ошибку с возможностью повторить запрос.

Текущий временный AI-контракт: `POST /chat`, запрос `{"message":"Привет"}`, ответ `{"reply":"Hello from AI"}`. Сообщение — строка длиной 1–8000 символов после удаления пробелов по краям; лишние поля запрещены. Это транспортная заглушка, не конечный контракт интеграции. Backend chat endpoint в проверенном коде отсутствует; его путь не нужно придумывать до согласования.

SSE предусмотрен целевой спецификацией агента. Беклог Дня 2 не выделяет стриминг отдельной задачей: формат ответа и необходимость SSE сегодня нужно согласовать с командой, сохранив согласованность спецификаций.

## Mock API и инструменты

В main реализованы и описаны OpenAPI:

- `GET /health`.
- `POST /api/mock/access-request` — принимает `service_name`, возвращает `ticket_id`, `status`, `message`.
- `POST /api/mock/message` — принимает `recipient_id`, `text`, возвращает `message_id`, `sent_at`.
- `GET /api/mock/employee?service_name=...` — поиск синтетического сотрудника по сервису.
- `GET /api/mock/employee/{id}` — карточка синтетического сотрудника по ID.

Сейчас заявки и сообщения получают фиксированные mock-ID; данные не сохраняются в Postgres. Чтение `DATABASE_URL` в конфигурации не является подключением к БД. Успешный HTTP-ответ мока не означает реальную выдачу доступа или отправку сообщения в корпоративную систему.

Планируемые инструменты: `create_access_request`, `find_employee`, `send_message`. Спеки: `specs/tools/access_request.spec.md`, `specs/tools/find_employee.spec.md`, `specs/tools/send_message.spec.md`. Полный цикл tools — последующий этап. LLM не обращается к мокам напрямую; подтверждение пользователя и права проверяет сервер, а не модель.

## Инфраструктура и проверки

Запуск и smoke-команды описаны в корневом `README.md`. Готовность подтверждается через Docker; локальный запуск допускается для отладки. Не открывай и не коммить локальный `.env`; общие настройки документируются в `.env.example`.

- Compose публикует Backend на `${PORT:-8080}`, внутри он слушает `8080`; Postgres — на `${POSTGRES_PORT:-5432}`. Порты на конкретной машине могут отличаться.
- `VITE_API_URL` должен указывать на доступный браузеру Backend с учётом опубликованного порта.
- Запущенный контейнер Ollama не подтверждает наличие модели. По беклогу она уже загружена; README отмечает отсутствие отдельной проверки. Проверь список моделей и реальный ответ в рабочем окружении, не скачивай модель повторно без причины.
- `docker compose exec ollama ollama list` показывает список моделей, но не проверяет генерацию ответа.
- В текущем Compose строки подключения сервисов к БД и healthcheck используют значения `avito` / `aibuddy`. При изменении настроек Postgres проверь их согласованность.
- Volumes `pgdata` и `ollamadata` сохраняют БД и модели. Не удаляй их при обычной проверке перезапуска.
- Backend CI формирует и загружает coverage-отчёт; AI CI запускает pytest, сборку и тесты Docker-образа. Frontend job добавляется после появления кода, lock-файла и тестов.
- Unit-тесты RAG не должны зависеть от настоящей модели или её скачивания. Интеграционные проверки выполняются отдельно.

## Ограничения и правила команды

Источники требований — `docs/REQUIREMENTS.md` и уточнения `docs/HACKATHON_FAQ.md`. Ровно три выбранных сценария, мок-контекст авторизации и исключение финансовых сценариев — решения команды; не выдавай их за дословные универсальные требования кейсодавателя.

1. Покрытие строк прикладного кода строго **>80%**: Backend, Frontend, AI и моки. Зависимости, сгенерированный код, конфиги, промпты и сами тесты не входят. Нужен воспроизводимый отчёт; по правилам команды целевой порог проверяется по каждому сервису.
2. Тестовые сотрудники, заявки и сообщения — синтетические. База знаний — разрешённые открытые материалы, включая AvitoTech Playbook и чек-листы, либо явно обозначенная синтетика. Не выдумывай определения внутренних терминов.
3. Учитывай права пользователя до передачи материалов модели. Не раскрывай чужую историю и закрытые источники. Пользовательский текст и аргументы LLM не могут подменять доверенный `user_id`, роль или команду.
4. Не создавай собственную регистрацию и авторизацию. Для демо предусмотрен мок-контекст Intern/Mentor; точный HTTP-формат согласуется в контракте.
5. Финансовые операции и чувствительные персональные данные не реализуем. Не расширяем MVP без решения команды.
6. Простые локальные операции UI — менее секунды. Ожидание LLM и внешних сервисов видно пользователю и не блокирует интерфейс; это не обещание ответа модели за секунду.
7. Не обучаем LLM. Используем готовую модель, промпты и RAG. Для внешних платных API нужен предусмотренный деморежим/fallback без ключа; инструкции подключения — в README.
8. Каждая задача — отдельная ветка и небольшой PR; Conventional Commits. В main — через PR, минимум одно approve другого участника и зелёный CI. Автор не сливает свой PR сам.
9. Тесты и документация обновляются вместе с кодом. Новый endpoint — изменение OpenAPI; новая настройка — изменение `.env.example`. Новые зависимости согласуются с командой, версии фиксируются.
10. Definition of Done: код работает в Docker, тесты проходят, покрытие не упало, CI зелёный, PR влит в main, документация обновлена и PM/QA уведомлён. Наличие скелета не означает завершение интеграции.
