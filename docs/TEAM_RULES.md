# Процесс разработки команды

> Правила, договорённости, Definition of Done.

---

## 1. Git-процесс (ветки, коммиты, PR)

| Правило | Конкретика |
|---|---|
| Ветки | Каждая задача — отдельная ветка: `feat/backend-mocks`, `feat/frontend-chat`, `feat/ai-rag`. В `main` — только через PR. |
| Коммиты | Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `chore:`. Пример: `feat(backend): add access-request mock`. |
| PR | Маленькие PR (до 300 строк). Один PR = одна задача. Merge — после зелёного CI и ревью одного человека (не автора). |
| Дедлайн merge | Каждый PR должен быть смержен в день создания. Не копим ветки — иначе конфликты. |
| Прямой push в `main` | Запрещён. |

*Зачем:* 4 человека × 5 дней = десятки коммитов. Без правил — конфликты и потеря времени.

---

## 2. Тесты — сразу, а не «потом»

| Правило | Конкретика |
|---|---|
| Пиши тест в том же коммите | Написал функцию `CreateAccessRequest` — в том же PR написал `TestCreateAccessRequest`. |
| Целевое покрытие | К концу дня 4 — `>80%` по каждому сервису (Go, React, Python). PM/QA проверяет ежедневно. |
| Что тестируем обязательно | Бизнес-логика (моки, RAG-поиск, обработка ошибок). Что не тестируем: UI-вёрстку (цвета, отступы), конфиги. |
| Красный CI = стоп | Если CI красный — все останавливаются и помогают починить. Нельзя мержить PR в красный `main`. |
| Инструменты | Go: `go test -cover`. React: `vitest --coverage`. Python: `pytest --cov`. |

*Зачем:* В ТЗ покрытие `>80%` для всего кода — это обязательное условие. Если оставить на день 4 — не успеем.

---

## 3. Ревью кода (кто, как быстро, что смотреть)

| Правило | Конкретика |
|---|---|
| Кто ревьюит | Backend ↔ AI (друг друга), Frontend ↔ PM/QA. Автор не мержит свой PR сам. |
| Что смотрим | Логика, тесты, обработка ошибок, соответствие `specs/`. Не придираемся к стилю (это делает линтер). |
| Аппрув | Минимум 1 approve + зелёный CI = можно мержить. |

*Зачем:* Без SLA ревью становится бутылочным горлышком. 30 минут — реалистично для хакатона.

---

## 4. Feature Freeze (заморозка фич)

| Правило | Конкретика |
|---|---|
| Дата | Исторический план: 14.10.2026 в 09:00. Дата прошла; актуальная заморозка должна быть подтверждена командой. |
| Что можно после freeze | Исправление багов, тесты, README, презентация, видео. |
| Что нельзя | Новые сценарии, новые эндпоинты, новые компоненты UI. |
| Исключение | Только по решению всей команды (голосование в чате, 3 из 4 «за»). |

*Зачем:* Последние 1.5 дня — на демо и защиту. Иначе 15-го будем чинить баги вместо записи видео.

---

## 5. Docker-first (всё работает в контейнере)

| Правило | Конкретика |
|---|---|
| Запуск только через Docker | `docker compose up --build` — единственный способ запуска. Локальные `go run` / `npm dev` — только для отладки, но не считаются готовностью. |
| Проверка на «чистой» машине | К концу дня 4 — `docker compose up` с нуля на ноутбуке другого человека. |
| Никаких «у меня работает» | Если не работает в Docker — значит, не работает. Фиксим, не отмахиваемся. |

*Зачем:* Жюри запускает проект на своём железе. Если у них не поднимется — 0 баллов за допуск.

---

## 6. Definition of Done (когда задача считается закрытой)

Задача закрыта, только если все пункты выполнены:

- [ ] Код написан и работает.
- [ ] Тесты написаны и проходят (покрытие не упало).
- [ ] CI зелёный.
- [ ] PR смержен в `main`.
- [ ] Документация обновлена (если нужно: `.env.example`, `README.md`, `specs/`).
- [ ] PM/QA уведомлён в чате.

*Зачем:* Убирает споры «а я думал, готово». Все понимают, что значит «сделано».

---

## 7. Документация — в том же коммите

| Правило | Конкретика |
|---|---|
| Новая переменная | Добавил в код — добавил в `.env.example` (в том же PR). |
| Новый эндпоинт | Обновил `specs/openapi.yaml` (в том же PR). |
| Новый сценарий | Обновил `docs/CJM.md` (в том же PR). |
| README | Обновляется каждый день (PM/QA), а не в конце. |

*Зачем:* Документация в конце — это «потом», которое не наступит. В том же коммите — единственный способ не забыть.

---

## 8. Зависимости (кто и как добавляет)

| Правило | Конкретика |
|---|---|
| Новая библиотека | Спрашиваем в чате: «Добавляю `pgvector-go` для X, ок?». |
| Запрещено | Тяжёлые фреймворки без необходимости (например, NestJS для 3 эндпоинтов). Лучше меньше зависимостей. |
| Фиксация версий | `go.mod`, `package-lock.json`, `requirements.txt` — всегда коммитим lock-файлы. |

*Зачем:* Случайная зависимость может сломать Docker-сборку или покрытие тестами.

---

## 9. Работа с ИИ (Управление контекстом LLM)

| Правило | Конкретика |
|---|---|
| Новый день = новый чат | В начале каждого рабочего дня открываем новый чат с LLM. Не тянем вчерашнюю историю с ошибками, старым кодом и тупиковыми ветками обсуждений. |
| Одна задача = один чат | Переключились с бэкенда на фронтенд? Открываем новый чат. Смешивание контекста (Go + React + Docker) перегружает модель и вызывает галлюцинации. |
| Ежедневный Kickoff | Шаблон промпта лежит в GitHub Issue на текущий день (`prompt.txt`). В начале дня открываем Issue, копируем промпт в новый чат LLM. Это гарантирует единый контекст для всей команды. |
| ИИ «затупил» = сброс | Если ИИ начал предлагать уже сделанное, забыл ограничения из ТЗ или путается в файлах — не спорим с ним. Открываем новый чат и кидаем Kickoff заново. |

*Зачем:* Контекстное окно LLM не бесконечное. Старые чаты отвлекают модель, замедляют ответы и провоцируют ошибки. Чистый чат + актуальный `PROJECT_CONTEXT.md` = максимальная точность и скорость.

---

## 10. Споры и решения

| Правило | Конкретика |
|---|---|
| Архитектурный спор | Обсуждаем 15 минут. Если не пришли к консенсусу — решает PM/QA (тайбрейкер). |
| «А давайте добавим…» | Применяйте актуально подтверждённый командой feature freeze; не выводите его статус из прошедшей даты 14.10.2026. Если заморозка не действует, решение о расширении MVP — голосованием 3 из 4. |
| Ошибка в проде | Не ищем виноватого. Фиксим, пишем в `docs/POSTMORTEM.md` (1 абзац), идём дальше. |

*Зачем:* На хакатоне время дороже правоты. Быстрое решение лучше идеального.
