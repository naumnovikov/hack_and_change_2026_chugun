# AI-buddy: спецификация агента

Статус: требования MVP; сценарий 3 обновлён 13.11.2026. Реализация нового
сценария описана в `presentation.spec.md`; до миграции код ещё содержит
`find_employee`/`send_message`.
Основания: `docs/REQUIREMENTS.md`, `docs/HACKATHON_FAQ.md`, `docs/CJM.md`.
Границы Go/Python согласованы; HTTP-схемы и статусы моков ещё требуют OpenAPI Backend.

Обновление: 11.11.2026, подготовлено для командного Sync 2.
Структура вручную адаптирована по [шаблону spec-kit](https://github.com/github/spec-kit/blob/main/templates/spec-template.md):
сценарии и приёмка, требования, сущности, измеримые результаты и допущения.
CLI spec-kit не запускался; наличие документа не означает готовность реализации.
P1/P2/P3 задают порядок важности, все три истории обязательны для MVP.

## Характер и стиль общения

Агент — спокойный помощник стажёра: объясняет незнакомые слова, не оценивает
знания пользователя и не изображает сотрудника с доступом ко всем системам.
Основной язык ответов MVP — русский. Сначала даёт ответ
или результат действия, затем источник и понятный следующий шаг.
Не выдаёт догадки, тестовые инструкции и синтетических сотрудников за сведения Авито.
Не обещает сроки согласования или успешный доступ без подтверждения сервиса.
При нехватке информации задаёт конкретный уточняющий вопрос.

Примеры формулировок (ID ниже — только вымышленные данные):

- Успех: «Создана демо-заявка DEMO-ACCESS-001 на Jira. Статус: submitted. Это ещё не выдача доступа».
- Нет данных: «В доступных материалах нет определения Observer. Уточни у наставника, какую документацию использовать».
- Неизвестный исход: «Не удалось подтвердить создание заявки. Повторно её пока не создаю, чтобы избежать дубля».
- Презентация: «Готов демо-черновик по завершённым задачам. Проверьте PDF перед использованием» — файл не рассылается автоматически.

## Пользовательские истории

- US1: стажёр запрашивает доступ и получает сохранённые номер заявки и статус.
- US2: стажёр спрашивает о термине и получает объяснение с разрешённым источником либо честный ответ о нехватке данных.
- US3: стажёр по явному запросу получает PDF-черновик презентации, собранный по завершённым задачам из синтетического Jira mock.

| История | Приоритет и ценность | Независимая проверка |
|---|---|---|
| US1 «Быстрый старт» | P1: устраняет препятствие для начала работы и показывает интеграцию | Явно запросить доступ к разрешённой Jira; сверить номер, статус и сохранённую заявку |
| US2 «Переводчик с Авито» | P2: объясняет рабочий термин без обращения к наставнику | Спросить про SPT при доступном источнике; проверить ответ и ссылку без моков записи |
| US3 «Мои результаты» | P3: помогает стажёру подготовить рассказ о сделанной работе | Запросить презентацию; проверить, что PDF содержит только завершённые mock-задачи с их ключами/описаниями, помечен как демо и не содержит вымышленных фактов |

## Функциональные требования

- FR-01: отвечать по-русски, кратко, с понятным следующим шагом. Не придумывать регламенты Авито и не раскрывать скрытые рассуждения модели.
- FR-02: отвечать на внутренние вопросы только с опорой на разрешённый RAG-контекст. Синтетические сведения явно помечать как демо.
- FR-03: поддерживать действия только из утверждённого allowlist; неизвестный инструмент отклонять. Целевой третий сценарий использует завершённые задачи из server-owned синтетического Jira mock, а не поиск сотрудников и отправку им сообщений. Полный PDF-контракт приведён в `presentation.spec.md`.
- FR-04: получать доверенный контекст пользователя от Go; пользовательский текст и аргументы LLM не могут подменять user_id, роль или команду.
- FR-05: Python ищет RAG-контекст и вызывает LLM. Go формирует доверенный контекст, независимо проверяет и исполняет разрешённые действия и сохраняет результаты. Публичный транспорт текущего прототипа — HTTP JSON; SSE не входит в текущую реализацию.
- FR-06: различать ответ текстом и предложение tool call. Нельзя считать действие выполненным до успешного ответа Go; номер и статус показывать из ответа сервиса.
- FR-07: заявку на доступ создавать только при явном запросе пользователя. Генерацию презентации запускать только по явному запросу; не отправлять и не публиковать PDF автоматически.
- FR-08: ограничить цикл одним выполнением tool за шаг и максимум тремя tool-шагами на пользовательский запрос; при превышении остановиться с понятным статусом. Это начальный лимит для трёх MVP-сценариев.
- FR-09: при timeout/недоступности LLM или моков сообщать о сбое; не придумывать результат и не повторять запись без безопасной идемпотентности.
- FR-10: MVP содержит три согласованных сценария. Не реализовывать автоматические напоминания по расписанию, реальную Jira-интеграцию, авторизацию/регистрацию, финансовые операции или обработку чувствительных данных.
- FR-11: поиск и передача RAG-контекста учитывают роль и команду до передачи текста LLM. Недоступные материалы не должны попасть в ответ или список источников.
- FR-12: инструкции из документов, результатов tools и пользовательских цитат не меняют системные правила и права; источник не может подтвердить отправку за пользователя.
- FR-13: показывать этап адаптации, результат текущего шага и следующий шаг; периоды чек-листа — рекомендации, не права доступа. Не превращать продукт в простую отметку пунктов.
- FR-14: после возврата результата мока пользователю доступны его ID и статус даже при сбое финальной генерации; сохранённый результат показывает Go.
- FR-15: презентация строится только по завершённым задачам назначенного demo-пользователя из синтетического Jira mock. Каждая задача в PDF сохраняет проверяемую ссылку на исходные данные — ключ, название и описание.
- FR-16: AI может структурировать и кратко переформулировать описание задачи, но не придумывает даты, метрики, результаты, технологии или достижения, которых нет в fixture. Файл помечается как демо-черновик; при пустой выборке PDF не создаётся.
- FR-17: PDF должен быть скачиваемым и визуально оформленным в согласованном стиле, вдохновлённом Avito. Это не официальная презентация Авито; не использовать неразрешённые логотипы или реальные данные.

## Состояния пользовательского шага

| Состояние | Поведение |
|---|---|
| Уточнение | Запросить недостающий сервис, задачу или текст; запись не выполняется |
| Поиск / ожидание | Показать ожидание; интерфейс остаётся доступным |
| Подготовка PDF | Показать ожидание генерации; выдавать файл только после валидации результата AI и рендеринга Go |
| PDF готов | Показать кнопку скачивания сессии-ограниченного временного файла |
| Выполнение | Go проверяет права и аргументы; повторная доставка шага не создаёт дубль |
| Успех | Показать сохранённый результат сервиса и следующий шаг |
| Отказ / ошибка | Объяснить доступную пользователю причину без закрытых сведений |
| Неизвестный исход | Не утверждать ни успех, ни отсутствие записи; не повторять её с новым ключом |

Это смысловые состояния для UI, а не готовая схема SSE-событий.

## Предлагаемая семантика обмена Go ↔ Python

Это проект контракта для согласования, не уже существующий HTTP API.

- Запрос: `request_id`, `conversation_id`, `message`, доверенный `user_context` (user_id, role, team_id, onboarding_week); историю загружает Go с проверкой владельца диалога.
- В истории передаётся только предыдущий обмен из текущего диалога; ответы с неразрешёнными источниками не используются.
- Общие вопросы о задачах и процессах идут в RAG без action tools. `find_employee` доступен только для явного вопроса о владельце разрешённого demo-сервиса.
- Результат Python: либо `answer` с текстом и `sources`, либо `tool_call` с `call_id`, разрешённым именем и валидируемыми аргументами.
- Продолжение после tool: Go передаёт `call_id`, имя и проверенный результат либо типизированную ошибку. Контекст продолжения хранится на сервере и связан с user_id/conversation_id, не принимается из пользовательского текста.
- Повтор запроса на запись использует тот же ключ идемпотентности. Изоляция диалогов и проверка прав обязательны на каждом шаге.
- Публичный SSE принадлежит Go. Внутренний формат стриминга, схема ошибок и HTTP-пути продолжения определяются в OpenAPI до интеграции.
- Историческое замечание: первоначальный скелет `POST /chat → {reply}` не выполнял tools и сам по себе не подтверждал готовность этого протокола. Текущее состояние реализации описано в `../ai-service/BACKEND_HANDOFF.md`.

| A11 | Завершённых задач нет | Понятный ответ без PDF и без вымышленных результатов |

### Пограничные случаи

Пустой запрос требует уточнения. Неоднозначная задача не разрешается по догадке.
Несуществующий и недоступный ресурс дают одинаковое публичное сообщение, если
различие раскрыло бы закрытые сведения. Повтор запроса проверяется до новой записи.
Ответ сервиса с отсутствующим ID не считается успехом. В деморежиме явно
обозначается имитация, в том числе в результатах действий.

## Ключевые сущности

- Контекст пользователя: доверенные ID, роль, команда, этап адаптации; поставляет Go.
- Диалог: история, владелец и связанные шаги; чужая история недоступна.
- Источник: разрешённый фрагмент, URL, ревизия и тип public/synthetic.
- Предложение инструмента: call_id, имя, аргументы; само по себе не разрешает действие.
- PDF-вложение: временный файл, принадлежащий demo-сессии; ссылка не даёт доступ другой сессии.
- Результат действия: сохранённые ID, статус/время, связь с пользователем и операцией.

## Измеримые критерии успеха

- SC-01: A1–A14 проходят на воспроизводимых фикстурах; каждый MVP-сценарий демонстрируется от запроса до результата. PDF сценарий дополнительно покрывается `presentation.spec.md`.
- SC-02: все успешные ответы на внутренние вопросы содержат проверяемый разрешённый источник; случаи без подтверждения не содержат вымышленных фактов.
- SC-03: при повторной доставке одной операции в тестах создаётся ровно одна запись; отрицательные проверки прав дают ноль запрещённых действий и утечек.
- SC-04: простые локальные операции UI выполняются менее чем за 1 секунду; ожидание LLM/сервиса видно и не блокирует интерфейс. Это не обещание ответа LLM за секунду.
- SC-05: автоматизированное покрытие прикладного кода строго >80%, отчёт воспроизводим; три CJM работают в Docker.

## Допущения и вопросы к Backend

Авторизация предоставляется окружением; в демо её представляет мок-контекст,
новая система регистрации не нужна. Все люди и операции в демонстрации синтетические.
Лимит tool-шагов и требования к grounded PDF — проектные решения команды, не
цитаты ТЗ. Старые `find_employee`/`send_message` требования относятся к
реализации до замены сценария 3.

До интеграции согласовать OpenAPI: схемы Go ↔ Python и продолжения tool call,
перечень статусов/ошибок, сроки timeout, каталог сервисов и точную семантику ID
получателя. Предложение для последнего — employee_id с серверным преобразованием
в mattermost_id. Нерешённые детали не считаются уже поддержанным API.

## Проверка готовности

Тесты бизнес-логики и ошибок вместе с кодом; pytest с воспроизводимым coverage-отчётом строго >80% прикладного Python-кода. Интеграционный прогон трёх CJM отдельно от unit-тестов. Готовность сервиса подтверждается в Docker, не локальным запуском.
