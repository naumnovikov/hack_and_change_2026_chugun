# Tool: create_access_request

Статус: семантический контракт для согласования с Backend; US1 / A1, A5, A7 из `../agent.spec.md`.

Обновление: 11.11.2026. Спецификация инструмента дополняет агентскую;
это описание ожидаемого поведения, не реализация и не утверждённый OpenAPI.

## Пользовательская история и проверка

Стажёр хочет запросить доступ из чата и получить номер, по которому можно
отследить заявку. Приоритет P1: без доступов он не может начать работу.
Независимая проверка: запросить разрешённый сервис и сверить ответ с записью
мока и сохранённым результатом Go, без RAG и отправки сообщений.

## Контракт

- Назначение: создать мок-заявку на доступ к выбранному сервису.
- Аргумент модели: `service_name` — непустое имя из разрешённого Backend каталога.
- `user_id` из исходного описания инструмента добавляет Go из доверенного контекста. LLM не выбирает пользователя; переданный ею user_id отклоняется как лишний аргумент.
- Адаптер Go: `POST /api/mock/access-request`; точный JSON закрепляется в OpenAPI Backend.
- Успех: `{ticket_id, status}` — непустые строки, допустимые статусы определяет OpenAPI.
- Операция создаёт заявку, не выдаёт доступ. Нельзя говорить «доступ получен» по одному факту создания.

| Поле | Источник и правило |
|---|---|
| service_name | Модель, после уточнения намерения; Go сверяет с разрешённым каталогом |
| user_id, role, team_id | Только доверенный контекст Go; из текста или tool-аргументов не принимаются |
| call_id и ключ идемпотентности | Серверный шаг диалога; сохраняются при сетевом повторе, LLM не выбирает новый ключ |
| ticket_id, status | Только валидированный ответ мока, сохраняются Go |

Пример предложения LLM: `{"service_name":"jira"}`.
Пример ответа мока: `{"ticket_id":"DEMO-ACCESS-001","status":"submitted"}`.
Это примеры синтетических значений; регистр имён и enum статусов утверждает Backend.

Порядок: явный запрос → уточнение сервиса → проверка контекста, каталога и прав
→ проверка повтора → вызов мока → проверка/сохранение результата → показ номера
и статуса. Вопрос «Как получить доступ?» сам по себе не разрешает создание заявки.

## Права и ошибки

- Только заявка текущего пользователя в доступный ему сервис. Проверка Go перед записью.
- Нет названия / неоднозначный сервис → уточнить. Запрещённый сервис → отказ без вызова.
- Go сохраняет ID и статус до успешного завершения шага; результат виден только владельцу/разрешённой роли.
- Ключ идемпотентности связан с пользователем, диалогом и call_id; повтор с теми же аргументами возвращает прежний результат, с другими — конфликт.
- Timeout с неизвестным исходом → сообщить о неопределённости; не создавать новую заявку с новым ключом автоматически.
- Ключ операции Go создаёт один раз и сохраняет до вызова; новый call_id от модели при повторной доставке того же шага не обходит защиту от дублей.
- Сбой сохранения после успешной записи в мок: не сообщать о завершённом шаге и не создавать новую операцию; восстановление использует тот же ключ. Мок/адаптер обязан поддерживать безопасный повтор по нему.

Смысловые ошибки: некорректный ввод, недоступный сервис, конфликт повтора,
недоступность сервиса, неизвестный исход, некорректный ответ мока, сбой сохранения.
Их HTTP-коды определяются в OpenAPI. Ответ пользователю не раскрывает наличие
закрытого сервиса; подробности ошибки доступны только разрешённой серверной диагностике.

## Приёмка / тесты

Явный запрос + разрешённый сервис → одна заявка, сохранённый номер и статус. Проверить пропущенное поле, чужой user_id, запрет, невалидный ответ мока, timeout, повтор с тем же ключом и конфликт аргументов. Ни один отрицательный случай не выдаётся за успех.

| ID | Дано → действие | Ожидается |
|---|---|---|
| AR-01 | Intern вправе запросить Jira → «Создай заявку на Jira» | Одна заявка, сохранены и показаны ID/статус; нет утверждения о выдаче доступа |
| AR-02 | Сервис не указан или неоднозначен → запрос доступа | Уточнение; ноль записей |
| AR-03 | Нет права на сервис или нет доверенного контекста → tool call | Отказ; ноль записей |
| AR-04 | В аргументах есть чужой user_id или неизвестное поле → tool call | Ошибка валидации; ноль записей |
| AR-05 | Заявка уже создана → повтор той же операции | Тот же результат; всего одна заявка |
| AR-06 | Тот же ключ, другие аргументы → повтор | Конфликт; исходная запись не изменена |
| AR-07 | Timeout после возможной записи → обработка ошибки | Неизвестный исход; нет слепого повтора с новым ключом |
| AR-08 | Ответ без ticket_id/status либо неизвестный status → обработка | Нет ложного успеха; сохранён контекст операции для восстановления |
| AR-09 | «Как получить доступ к Jira?» → вопрос о порядке | Объяснение по источнику либо уточнение, заявка не создаётся |
| AR-10 | Мок записал заявку, сохранение в Go упало → безопасный повтор | Не больше одной заявки, результат восстанавливается с тем же ключом |

## Сущности, критерии и зависимости

Сущности: разрешённый сервис, операция с ключом повтора, заявка текущего пользователя.
Готовность: AR-01–AR-10 проходят, повтор не создаёт дубль, успешный результат
переживает повторное чтение диалога владельцем. Go и мок проверяются тестами;
покрытие прикладного кода строго >80% и воспроизводимый Docker-прогон обязательны.
До реализации Backend утверждает каталог, статусы, timeout и механизм идемпотентности
в OpenAPI. Доступы к реальным корпоративным сервисам эта спецификация не выдаёт.
