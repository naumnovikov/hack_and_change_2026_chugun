# Tool: find_employee

Статус: семантический контракт для согласования с Backend; US3 / A4, A5 из `../agent.spec.md`.

## Контракт

- Назначение: найти ответственного за микросервис в синтетическом реестре команды.
- Аргумент модели: `service_name` — непустая строка, разрешённый сервис.
- Семантический результат: `{employee_id, name, role, mattermost_id}`. `employee_id` нужен для однозначной связи с HTTP-моком; это предлагаемое дополнение к краткой форме из PROJECT_CONTEXT.
- В CJM указан `GET /api/mock/employee/{id}`: он получает сотрудника по ID, но сам не разрешает имя сервиса в ID.
- Предложение для Backend: разрешать task → service → employee_id в серверном синтетическом реестре, затем вызывать существующий employee-мок. Новый HTTP-эндпоинт не требуется без отдельного решения.
- Канонический recipient_id для send_message (employee_id или mattermost_id) должен быть явно выбран в OpenAPI; LLM не конструирует его самостоятельно.
- Для Sync 2 в send_message предложен employee_id с преобразованием в mattermost_id на стороне Go. Это ещё не утверждённый Backend-контракт; при другом выборе синхронно обновить обе tool-спеки и OpenAPI.

## Права и ошибки

- Только чтение. Go ограничивает поиск доступными пользователю сервисами и полями сотрудника; Python не читает закрытый реестр напрямую.
- Если сервис не указан или вариантов несколько — уточнить. При отсутствии владельца — сообщить об отсутствии данных и направить к наставнику.
- Недоступные записи не раскрывать через различие ошибок «существует»/«не существует».
- Не придумывать владельца по названию сервиса и не выдавать синтетических людей за сотрудников Авито.

## Приёмка / тесты

Разрешённая задача из фикстуры приводит к заданному сервису и владельцу. Проверить неизвестную задачу, неоднозначность, отсутствие owner, чужую команду, запрещённые поля и timeout. Сам поиск не отправляет сообщение; отправка — отдельный подтверждённый шаг.
