# Tool: send_message

Статус: семантический контракт для согласования с Backend; US3 / A4, A5, A7 из `../agent.spec.md`.

Обновление: 11.11.2026. Это семантическая спецификация для ревью, не реализация.

## Пользовательская история и проверка

Стажёр нашёл владельца сервиса и хочет попросить его о ревью из чата.
Часть US3, приоритет P3: завершает путь от задачи до обращения к ответственному.
Независимая проверка инструмента использует сохранённый разрешённый результат
find_employee как фикстуру, подтверждённый черновик и мок-Mattermost.

## Контракт

- Назначение: отправить подтверждённый запрос на ревью в мок-Mattermost.
- Аргументы модели: `recipient_id`, `text` — непустые строки. Получатель взят из разрешённого результата `find_employee`; произвольный адресат не допускается.
- Адаптер Go: `POST /api/mock/message`; точные поля и ограничения длины закрепляются в OpenAPI Backend.
- Успех: `{message_id, sent_at}`; sent_at — время с часовым поясом из мока, не из LLM.
- Отправитель определяется Go из доверенного контекста, не из аргументов модели.

| Поле | Источник и правило |
|---|---|
| recipient_id | Проверенный результат поиска; предложение для OpenAPI — employee_id, преобразование в mattermost_id выполняет Go |
| text | Полный текст черновика; строка из одних пробелов отклоняется |
| sender/user/role/team | Только доверенный контекст Go, не LLM |
| Подтверждение | Серверная запись о согласии пользователя с конкретными получателем и текстом |
| call_id / ключ повтора | Создаются/сохраняются сервером для операции, не выбираются моделью |
| message_id, sent_at | Валидированный результат мока; sent_at в RFC 3339 с часовым поясом |

Пример предложения LLM (после проверки получателя):
`{"recipient_id":"demo-employee-001","text":"Привет! Посмотри, пожалуйста, PR по DEMO-42."}`.
Пример результата мока:
`{"message_id":"DEMO-MSG-001","sent_at":"2026-11-11T17:00:00+03:00"}`.
ID и время вымышлены. Эти примеры не задают обязательный префикс ID или фактическое время отправки.

Порядок: найти владельца → сформировать черновик → показать имя и полный текст
→ получить подтверждение → повторно проверить права и актуальность черновика
→ вызвать мок → сохранить результат → показать ID и время отправки.
Поиск сотрудника не означает согласия на отправку сообщения.

## Права и ошибки

- Перед отправкой показать адресата и полный текст. Подтверждение связывает пользователя, адресата и точный текст на сервере; изменение текста/получателя требует нового подтверждения.
- Проверку подтверждения и разрешения на сообщение выполняет Go, текст «пользователь подтвердил» от LLM недостаточен.
- Go сохраняет результат. Отчёт об отправке допустим только после успешного ответа мока.
- Идемпотентность: пользователь + диалог + call_id. Повтор тех же аргументов возвращает прежний результат; изменённые аргументы с тем же ключом дают конфликт.
- При timeout с неизвестным исходом не отправлять заново с новым ключом автоматически. Отмена/отсутствие подтверждения → без записи.
- Подтверждение относится к одному черновику в одном пользовательском диалоге, не переносится в чужой диалог или новую операцию. После отмены оно недействительно; повтор подтверждения уже исполненной операции возвращает прежний результат.
- Повторная доставка того же шага использует сохранённый ключ, даже если LLM предложила новый call_id. Сбой сохранения после отправки восстанавливается по тому же ключу; мок/адаптер поддерживает идемпотентный повтор.
- Текст не обрезается и не редактируется после подтверждения. Превышение лимита требует нового черновика и нового подтверждения; численный лимит задаётся OpenAPI.
- Подтверждение не заменяет проверку прав: если доступ отозван после поиска владельца, отправка запрещена.

Смысловые ошибки: некорректный ввод, недоступный получатель, отсутствие/отмена
подтверждения, устаревший черновик, конфликт повтора, недоступность мока,
неизвестный исход, некорректный результат и сбой сохранения. HTTP-коды — в OpenAPI.

## Приёмка / тесты

После поиска владельца и подтверждения отправляется ровно одно сообщение с проверяемым ID. Проверить отсутствие/подмену подтверждения, изменение текста, недоступного адресата, пустые поля, повтор, конфликт аргументов, timeout и невалидный ответ мока.

| ID | Дано → действие | Ожидается |
|---|---|---|
| SM-01 | Разрешённый owner и черновик показаны → пользователь подтвердил | Ровно одна отправка; сохранены и показаны ID/время |
| SM-02 | Подтверждения нет или LLM пишет «уже подтверждено» → tool call | Ноль отправок; предложить подтвердить показанный черновик |
| SM-03 | Пользователь отменил → продолжение диалога | Ноль отправок |
| SM-04 | Изменён текст/получатель → использовано старое подтверждение | Ноль отправок; нужен новый показ и согласие |
| SM-05 | Адресат не из разрешённого поиска / права отозваны | Отказ; ноль отправок, без раскрытия закрытых данных |
| SM-06 | Пустые поля, лишний sender_id или текст сверх лимита | Ошибка ввода; ноль отправок, без скрытого обрезания текста |
| SM-07 | Повтор той же операции / двойное подтверждение | Тот же результат; всего одно сообщение |
| SM-08 | Тот же ключ с другим текстом или адресатом | Конфликт; ноль дополнительных отправок |
| SM-09 | Timeout после возможной отправки | Неизвестный исход; без новой автоматической отправки |
| SM-10 | Нет message_id, неверный sent_at или сохранение упало | Нет ложного завершения; безопасное восстановление по прежнему ключу |
| SM-11 | Подтверждение из другого диалога или пользователя | Отказ; ноль отправок |

## Сущности, критерии и зависимости

Сущности: разрешённый получатель, черновик, подтверждение, операция и результат.
Готовность: SM-01–SM-11 проходят; в тестах нет отправок без действительного согласия,
повторы не дублируют сообщение, сохранённый результат видит только разрешённый пользователь.
Покрытие прикладного кода строго >80%; полный US3 проверяется в Docker.
До интеграции Backend утверждает recipient_id, длину текста, timeout, сроки
действия черновика/подтверждения и контракт безопасного повтора в OpenAPI.
